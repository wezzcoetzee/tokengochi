Pacing & the Overfed Pet

Reward people who get the most value out of their subscription — without celebrating the user who blows their 5-hour window in the first hour and then sits idle. A three-axis model that keeps weekly usage as the reward and makes pace the thing that decides how good it feels.

01Goal

Confirmed direction:

Reward maximum value extracted from the subscription — high weekly usage is good, because unused quota is value left on the table.

But discourage front-loading — hitting ~100% of a session window with hours left on the clock, then sitting rate-limited and idle, is not "getting the most use." It's wasting the window.

The insight: these are two separate axes the current engine collapses into one number. How much you use (weekly) is the reward. How well you pace it (session vs. time left) decides comfort.

02What's wrong today

The stuffed reward celebrates the anti-pattern

In PetEngine.swift:146 the "maxed" check fuses two opposite situations with one ||:

let maxed = session >= maxedThreshold || weekly >= maxedThreshold  // 95%
SituationRealityToday
weekly ≥ 95%Extracted huge value this week — your ideal userreward ✓
session ≥ 95% earlyBurned the window, now locked out & idle for hoursalso "reward" 😴 — wrong

The stuffed pet literally naps until reset — the on-screen embodiment of the idle behavior we want to discourage.

There is no concept of pace at all

The engine only sees session as a point-in-time number. It cannot tell these apart:

95% session, 4 hours left → front-loaded, about to idle (bad)

95% session, 10 minutes left → paced perfectly all window (ideal)

Both produce identical stuffed today. Encoding pace is the whole job.

03The three-axis model

Reward

driven by · weekly %
Are you getting value from the sub?

lonely → okay → thriving

Comfort

driven by · session pace
Are you using the window well?

starving → content → overfed

Health

driven by · messes
Are you neglecting cleanup?

healthy → sick
Critical: happiness is min(100, weekly × 1.1), so a heavy user is pinned at 100 from weekly alone. If pacing only nudges happiness, the front-loading penalty is invisible to exactly the power users most likely to front-load. Pacing must be able to cap the reward, not just add to it. Weekly sets the ceiling; pace decides how much of it you enjoy right now.

04Pace math

No new data needed — both window bounds are already persisted (start = lastSessionResetsAt, end = sessionResetsAt).

let f      = (now - start) / (end - start)   // fraction of window elapsed, 0…1
let target = f * 100                       // where you'd be if pacing to fill the window
let delta  = session - target               // ahead (+) or behind (−) pace
deltaMeaningComfort state
≈ 0Filling the window steadily — idealcontent / thriving
strongly +Front-loaded; headed for forced idleoverfed
negativeBehind pace; leaving quota unusedstarving / hungry
Free bonus: at window start f ≈ 0 and session ≈ 0, so delta ≈ 0 — "on pace," not starving. This also fixes the jarring thriving → starving flip that fires every 5 hours under the current absolute-session logic.

Edge cases: first window (lastSessionResetsAt == nil) → treat pace as neutral until a window boundary exists. Guard end > start to avoid divide-by-zero.

05The "overfed" mechanic new

Front-loading makes the pet fat and uncomfortable — not sick. Health stays exclusively the messes axis (100 − messes × 20) so the mental model "sick = you ignored cleanup" stays clean.

Trigger

let overfed = session >= 90 && f < 0.8
// near the cap AND more than ~1 hour left in the 5h window

let severity = (0.8 - f) / 0.8   // 0 at the 1h-left boundary → 1 at window start

Calibrated to: 95% / 4h left = overfed, 90% / 1h left = the good boundary, 95% / 10m left = ideal. The session ≥ 90 gate keeps the lockout real — being ahead of pace only hurts once you're actually near the ceiling. severity grades the bloat so maxing at 4h-left is fatter than maxing at 90 minutes left (no hard cliff).

Consequences

  • Weight gets a healthy band. Today weight is purely cosmetic (min(1, (weekly·0.7 + session·0.7)/100)). Front-loading inflates it past the band, scaled by severity → visibly bloated.
  • Happiness is capped while overfed, scaled by severity: min(happiness, 50 + (1 − severity)·40) — a ~50 ceiling for maxing at window start, easing back toward normal near the 1h-left boundary. Even a weekly-maxed power user feels the bloat. This is the "pace must override the reward" rule in action.
  • Health untouched. Start with happiness + weight only — already a real, visible penalty. We can add a small health touch later if it needs to bite harder.

06Mood resolution (priority order)

  1. 🥚noData — no snapshot yet
  2. 🤒sick — messes, health < 40 — real neglect, always wins
  3. 🐷overfed new — front-loaded: big positive pace delta with time left
  4. 😄thriving / okay / lonely — weekly bands (top of thriving absorbs the old weekly-maxed "crushing it")
  5. 🍴starving — significantly behind pace / barely used
Retire the sleepy stuffed nap. Weekly-maxed becomes the top of thriving; session-maxed-early becomes overfed. The napping animation was the literal picture of the idle behavior we're discouraging.
